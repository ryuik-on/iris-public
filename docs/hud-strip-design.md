# IRIS HUDストリップ設計案

## 1. 目的と前提

HUDストリップは、フルスクリーンアプリの上にも常時表示する高さ1〜3行の細い帯である。利用者がチャットを開かなくても、IRISの現在の進み具合と、次に必要な行動を把握できることを目的とする。

この帯では個別の作業名や識別子を一覧にせず、「何件が、どの状態か」を主語にする。タスク番号のような利用者が意味を記憶していない情報は表示しない。例文中の件数は説明用のサンプル値であり、実際には各APIの現在値に置き換える。

利用できるデータ源は、すべて `http://127.0.0.1:3002` の次のローカルAPIに限る。

- `/api/portfolio`: Project名、完了数、停止数、停止理由、台帳未登録リポジトリ
- `/api/agent/runs`: 実行中エージェント、ブランチ、費用
- `/api/approvals/pending`: 承認待ち一覧
- `/api/proactive`: 提案一覧
- `/api/calendar`: 次の予定のタイトルと時刻
- `/api/context`: 現在わかっていることと確信度
- `/api/budget`: 当日の支出と上限
- `/api/usage/cli`: CodexとClaudeの週次消費パーセント
- `/api/delegation`: 委任の有無と当日の消化額
- `/api/sessions`: この端末で動いているClaude / Codexのセッションと、最後に動いてからの分数
- `/api/weather`: 現在の天気（ショートカット経由）
- `/api/travel/next`: 次の予定の行き先。移動時間は帯の側でMapKitが測る

天気は実装済みである（2026-08-22）。macOSは予報をAPIとして渡さないため、`shortcuts run` でユーザー自身が作ったショートカットを呼び、その出力文字列を読む。位置情報も同様に実装済みで、`IRIS HUD.app` がCoreLocationの許可を持ち、MapKitで次の予定までの経路時間を計算する。**どちらも本書の初版が「存在しない」と書いた前提を覆している。**

依然として存在しないのは、ニュースと外部の稼働監視である。

本書は初版の判断を残したまま追記している。消していないのは、当時「天気は未実装・要判断」と判断したこと自体は正しく、その判断が何によって覆ったかを残す方が、書き直して痕跡を消すより後から役に立つためである。

## 2. 案A：ステータスバッジ中心

### ねらい

短いバッジを横一列に並べ、緊急性の高い状態だけを色で拾える案である。情報密度は高めだが、文章を読まずに「動いているか」「自分の操作が必要か」を判断できる。高さは1行を基本とし、画面幅が狭い場合は重要度の低いバッジを折りたたむ。

### literalな表示例

以下は画面に実際に表示される文字列の例である。

| 状態 | 表示例 |
|---|---|
| アイドル | `● 待機中　完了 8件　停止 0件　次は 14:30「薬理学の復習」` |
| エージェント実行中 | `● 実行中 2件　完了 8件　費用 ¥120　次は 14:30「薬理学の復習」` |
| 承認待ち | `● 承認待ち 1件　実行中 2件　停止 0件　確認が必要です` |
| 提案あり | `● 提案 3件　実行中 0件　完了 8件　次の一手があります` |
| IRIS無応答 | `○ 接続を確認中　現在の状態を取得できません` |
| 実行中かつ承認待ち | `● 実行中 2件　承認待ち 1件　提案 3件　確認が必要です` |

### 各要素のデータ出所

- `● 待機中`、`● 実行中 2件`：`/api/agent/runs` の実行中エントリ数。0件なら「待機中」、1件以上なら「実行中」とする。
- `完了 8件`：`/api/portfolio` の完了数の合計。
- `停止 0件`：`/api/portfolio` の停止数の合計。停止理由は帯には残さず、詳細画面で確認する。
- `費用 ¥120`：`/api/agent/runs` の費用フィールドの合計。通貨と丸め規則は実データの定義に合わせる。
- `承認待ち 1件`：`/api/approvals/pending` の一覧件数。
- `提案 3件`：`/api/proactive` の提案一覧件数。
- `次は 14:30「薬理学の復習」`：`/api/calendar` の次の予定の時刻とタイトル。予定がない場合の「次はありません」は同APIが空一覧を返した場合だけ表示する。
- `確認が必要です`：承認待ち一覧が1件以上という状態から生成する定型文。追加のデータ源はない。
- `次の一手があります`：提案一覧が1件以上という状態から生成する定型文。追加のデータ源はない。
- `○ 接続を確認中　現在の状態を取得できません`：列挙したローカルAPIへの要求がタイムアウトまたは通信エラーになったというUIの取得状態。バックエンドの詳細原因はデータ源なし。

## 3. 案B：1行サマリー＋所感ローテーション

### ねらい

一行目を人が読みやすい要約、二行目を静かな所感に固定する案である。バッジより温度感があり、勉強や作業の邪魔をしにくい。所感は一定間隔でローテーションするが、承認待ちや無応答時は状態表示を優先してローテーションを止める。高さは2行を基本とする。

### literalな表示例

| 状態 | 表示例 |
|---|---|
| アイドル | `いまは待機中。完了 8件、停止 0件。`<br>`次は14:30「薬理学の復習」。それまで少しずつ進めよう。` |
| エージェント実行中 | `2件の作業が進行中。費用は¥120。`<br>`次は14:30「薬理学の復習」。手は動いています。` |
| 承認待ち | `承認待ちが1件あります。`<br>`確認できるものが届いています。` |
| 提案あり | `提案が3件あります。実行中の作業はありません。`<br>`次の一手を選べます。` |
| IRIS無応答 | `IRISに接続できません。`<br>`表示を更新できるまで、現在の画面を保っています。` |
| 実行中かつ承認待ち | `2件の作業が進行中。承認待ちが1件あります。`<br>`まず確認が必要なものがあります。` |

### 各要素のデータ出所

- `いまは待機中`、`2件の作業が進行中`：`/api/agent/runs` の実行中エントリ数。
- `完了 8件、停止 0件`：`/api/portfolio` の完了数と停止数の合計。
- `費用は¥120`：`/api/agent/runs` の費用フィールドの合計。
- `承認待ちが1件あります`：`/api/approvals/pending` の一覧件数。
- `提案が3件あります`：`/api/proactive` の提案一覧件数。
- `次は14:30「薬理学の復習」`：`/api/calendar` の次の予定の時刻とタイトル。
- `それまで少しずつ進めよう`、`手は動いています`、`確認できるものが届いています`、`次の一手を選べます`：それぞれの状態に対する定型の所感。外部データは使わない。
- `IRISに接続できません`、`表示を更新できるまで、現在の画面を保っています`：ローカルAPI要求の通信エラーまたはタイムアウトと、最後に正常取得できた表示を保持するUI状態。保持された内容の時点は別途画面内に出さず、古い値を最新値と誤認させない。
- `予定がない`場合の所感は、`/api/calendar` が空一覧を返した時だけ「予定は入っていません。自分のペースで進めよう。」とする。時刻・曜日以外の雑談を外部から補わない。

## 4. 案C：ミニマル記号＋色

### ねらい

文章を極限まで短くし、左端の状態記号、中央の数値、右端の一言で構成する案である。情報密度は低めで視認性が高く、暗い背景のフルスクリーンアプリにも馴染む。高さは1行、必要なときだけ2行目に行動要求を出す。

### literalな表示例

| 状態 | 表示例 |
|---|---|
| アイドル | `◇ 待機　完了8　停止0　次 14:30「薬理学の復習」` |
| エージェント実行中 | `◌ 稼働　実行2　費用¥120　進行中` |
| 承認待ち | `! 確認　承認1　今ひとつ確認できます` |
| 提案あり | `✦ 提案　3件　次の一手あり` |
| IRIS無応答 | `— IRIS　更新停止　接続を確認中` |
| 実行中かつ承認待ち | `! 稼働　実行2　承認1　確認を優先` |

### 各要素のデータ出所

- `◇ 待機`、`◌ 稼働`：`/api/agent/runs` の実行中エントリ数が0か、1件以上か。
- `完了8`、`停止0`：`/api/portfolio` の完了数と停止数の合計。
- `次 14:30「薬理学の復習」`：`/api/calendar` の次の予定の時刻とタイトル。
- `実行2`：`/api/agent/runs` の実行中エントリ数。
- `費用¥120`：`/api/agent/runs` の費用フィールドの合計。
- `! 確認`、`承認1`：`/api/approvals/pending` の一覧件数が1件以上であることと、その件数。
- `✦ 提案`、`3件`：`/api/proactive` の提案一覧件数。
- `進行中`、`今ひとつ確認できます`、`次の一手あり`、`確認を優先`：各状態から生成する定型ラベル。外部データは使わない。
- `— IRIS　更新停止　接続を確認中`：列挙したローカルAPIへの通信エラーまたはタイムアウト。原因の詳細はデータ源なし。更新停止は、無応答中に古い数値を新しい値として再表示しないためのUI状態である。

## 5. 雑談・所感の扱い

**この段落は2026-08-22に覆った。** 初版の時点では天気データ源がなく、天気を事実として表示しない判断は正しかった。現在はショートカット経由で取得しており、帯の右端に表示している。位置情報も `IRIS HUD.app` が許可を持つため、場所に依存する表現（次の予定までの移動時間）も表示できる。

今回採用可能な代替は、既存の情報だけに基づく次のような所感である。

- `次は14:30「薬理学の復習」。「それまで少しずつ進めよう。」`：予定のタイトルと時刻は `/api/calendar`。後半は状態に応じた定型文で、追加の事実を主張しない。
- `提案が3件あります。次の一手を選べます。`：件数は `/api/proactive`、後半は一覧が空でないことからの定型文。
- `承認待ちが1件あります。確認できるものが届いています。`：件数は `/api/approvals/pending`、後半は承認操作が必要という状態からの定型文。

予定の内容を所感に使う場合も、`/api/calendar` が返したタイトルをそのまま長く読み上げず、短い表示長に切り詰める。`/api/context` を使う場合は確信度が十分高い情報だけを採用し、確信度が低いものは「確かめ中」といった断定しない表示にする。データ源のない気分・天候・位置・ニュースを生成して事実のように表示しない。

## 6. 狭い帯での情報優先順位

高さ1〜3行では、次の順で残す。

1. **バックエンド無応答・更新不能**：最優先。何も表示しないと利用者は「止まっている」のか「問題がない」のか判断できないため。ただし「障害」「失敗」と大きく煽らず、「接続を確認中」「現在の状態を取得できません」と伝える。
2. **承認待ちなど利用者の行動が必要な状態**：次に優先。行動要求がある情報は、単なる進捗より見逃しコストが高い。件数を表示し、個別内容はチャットや詳細画面に委ねる。
3. **実行中の件数と費用**：進行状況を知るという目的の中心。個別のエージェント名、ブランチ、費用内訳は帯から削る。
4. **提案の件数**：注意を向ける価値はあるが、通常は承認待ちより緊急性が低い。「提案 3件」のように数だけ残す。
5. **完了数・停止数**：進捗の背景を短く示す。停止理由は認知負荷が高く、かつ長くなりやすいため、停止があることだけを帯に残す。
6. **次の予定と短い所感**：利用者の作業リズムに役立つが、行動要求のない場合は最後に置く。狭い幅では所感を削り、予定の時刻と短いタイトルを優先する。
7. **補助指標**：台帳未登録リポジトリ、`/api/context` の詳細、`/api/budget` の当日支出と上限、`/api/usage/cli` の週次残量、`/api/delegation` の委任と当日消化額は、重要な閾値を超えたときだけ差し込む。平常時は帯に載せず、詳細画面に置く。

優先度の基準は、第一に緊急性、第二に利用者の行動要求、第三に見逃し時の損失、第四に一目で理解できるか、第五に認知負荷である。数値は状態の変化を短く表せるため残すが、個別名や理由は帯の幅を消費する割に判断を完了できないため削る。

## 7. スタイリッシュさの実現方針

全案とも、帯をアプリの主役ではなく「薄いインフラ」として扱う。背景は黒に近いチャコールまたは半透明の濃紺、文字は暖色寄りの白にし、長時間の暗所利用でまぶしくならないよう純白を避ける。状態色は、正常を低彩度の青緑、実行中を青、承認待ちを琥珀、無応答を落ち着いた灰色とし、赤はデータ消失など本当に危険な状態に限定する。色だけに意味を持たせず、記号と短いラベルも併記する。

フォントは小サイズでも数字と日本語の字形が崩れにくいサンセリフ系を基本とし、件数・時刻は等幅寄りの数字で揃える。文字サイズは本文より一段小さくしつつ、最小サイズを設けて可読性を守る。左右の余白は均等にし、要素の間隔を一定にする。角丸や細い境界線は控えめに使い、情報のグループを示すためだけに用いる。

状態の変化には短いフェードまたは位置を変えない色の遷移だけを使い、常時点滅、横スクロール、頻繁な数字の跳ねは使わない。実行中の記号は必要ならごく弱く脈動させるが、承認待ちでも点滅させず、視線を奪いすぎない。無応答時も帯全体を赤くせず、淡い灰色の接続表示にすることで不安を煽らない。暗所では背景とのコントラストを確保し、色覚差があっても記号・文言で状態を判別できるようにする。

## 8. API利用と状態遷移の注意

複数APIを同時刻に取得できない場合、帯に表示する数値の時点が混在しうる。そのため、更新は一括で受け取れたスナップショット単位を基本とし、取得に失敗した項目だけを勝手に0件へ置き換えない。部分取得なら「一部を更新できません」とするか、最後の正常スナップショットを保持して更新時刻を示す設計判断が必要である。

`/api/portfolio` の停止理由、`/api/agent/runs` のブランチ、`/api/delegation` の消化額など、帯に載せないフィールドは詳細画面への導線に使う。`/api/budget` と `/api/usage/cli` は上限に近づいた場合だけ、たとえば「今日の予算残り 10%」「週次残量 15%」のように差し込む。ただし、閾値・丸め・警告文は別途プロダクト判断が必要である。

## 9. 3案の比較と推奨

| 案 | 情報密度 | トーン | 向いている場面 | 主な弱点 |
|---|---:|---|---|---|
| A：ステータスバッジ中心 | 高 | 即時・機能的 | 多数の状態を一目で監視したいとき | 数字が並ぶと冷たく見えやすい |
| B：1行サマリー＋所感ローテーション | 中 | 人間的・落ち着き | 勉強や作業の横で常時見せるとき | 文章が長いと幅を超えやすい |
| C：ミニマル記号＋色 | 低〜中 | 静か・洗練 | 画面を極力邪魔したくないとき | 記号の意味を初回に学ぶ必要がある |

今回の目的には、**案Bを推奨**する。利用者は監視ダッシュボードを見たいのではなく、勉強中に作業の進み具合を知りたいので、2行の自然な要約と短い所感が最も適している。承認待ち・無応答では所感を止め、行動要求と接続状態を優先する。画面幅が極端に狭い場合は案Cの短縮表現へ切り替え、多数の運用状態を監視するモードでは案Aを選べるようにする。

**この結論は2026-08-22に覆った。** 挙げられた4点は、いずれも実装時に判断が必要だという指摘として正しかった。実際の答えは次のとおりである。

- **取得先**: macOSは予報をAPIとして渡さない。`~/Library/Weather/weather-data.db` は現在の天気を持つが、`model` 列は623バイトの非公開バイナリで、8バイトのdoubleが2つ（時刻）だけ解け、残りは解けない。解析すればOS更新のたびに壊れる読み取り器になる。したがってショートカット経由とした。
- **位置情報の扱い**: 座標は端末外に出ない。天気はショートカットがApple内部で処理し、移動時間は `IRIS HUD.app` 内のMapKitがAppleのサーバに渡す。第三者の経路サービスは使わない。
- **更新頻度**: 天気は15分キャッシュ。移動時間は5分（渋滞が変わるため）。失敗は60秒しか保持しない。成功と失敗を同じ寿命にすると、一瞬の失敗が原因の消えた後も15分居座る。
- **障害時の代替表示**: 「取得できません」と理由を出す。空欄にはしない。**予報がないことと、ショートカットが消えていることは外から見分けがつかず、待って直るのは片方だけである。**

## 8. 実際に採用した配置（2026-08-22）

高さ50pt、2行。左から右へ:

```
[コア 36pt] [IRIS] [見出し / 予定・移動] ……… │ [CLAUDE nn% CODEX nn%] │ [天気]
```

1行目の優先順位は、承認待ち → 稼働中 → 提案 → 待機。件数の出どころは台帳ではなく `/api/sessions` である。**台帳の「進行中」は人が手で立てる欄で、立て忘れると稼働中の端末が「着手中のものはありません」と表示する。** 観測できるものを観測する。

止まっているタスクは件数ではなく題名を出す。件数だけでは「どれか分からない」という不満が残り、実際に残った。

タスクごとの進み具合は帯に載せず、ダッシュボードに送った。50pt2行では複数の題名と状態を同時に読めない。
